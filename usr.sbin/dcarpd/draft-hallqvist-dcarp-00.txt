    DCARP: Distributing Dynamic Addresses to CARP Redundancy Groups
                        draft-hallqvist-dcarp-00

Abstract

   The Common Address Redundancy Protocol (CARP) lets a group of hosts
   share IP addresses, but every member must be configured with the
   shared addresses in advance.  When the shared address is assigned
   dynamically, for example by DHCP to the current master, the backups
   do not know it, and since CARP authenticates its advertisements over
   the shared addresses, a change of the address splits the group into
   several masters.  The Distributed Common Address Redundancy Protocol
   (DCARP) lets the master distribute the shared IPv4 address, its
   netmask and the gateway of its network, together with the master's
   address on another network the members share, which they route
   through while they are backups, to the other members, encrypted and
   authenticated, and resolves the split that follows an address change.

1.  Introduction

   CARP [CARP], like VRRP [RFC9568], makes a group of hosts share one or
   more virtual addresses on a network.  One member, the Master, owns
   the addresses and answers for them; the others, the Backups, take
   over when the Master stops sending advertisements.  CARP requires
   that all members are configured with the same virtual addresses.









Hallqvist                  Expires 26 May 2027                  [Page 2]

Internet-Draft                    DCARP                    November 2026


   That requirement cannot be met when the shared address is assigned
   dynamically.  A typical case is a pair of firewalls whose external
   address is assigned by an Internet service provider with DHCP
   [RFC2131]: the DHCP client runs on the CARP interface of the Master,
   which shares a virtual MAC address with the Backups, and only the
   Master learns the address.  Two problems follow:

   1.  A Backup that becomes Master does not know the address, its
       netmask or the gateway of that network, and cannot use them until
       it completes a DHCP exchange of its own.

   2.  CARP authenticates its advertisements over the set of virtual
       addresses.  When the Master's address changes, the Backups reject
       its advertisements, conclude that the Master is gone, and become
       Masters themselves.  The group stays split until an operator
       intervenes.

   A Backup cannot use the provider's gateway either: its CARP interface
   passes no traffic.  It routes through the Master over another network
   the members share, typically an internal one, and needs the Master's
   address there.

   DCARP solves these problems.  The Master sends the address, its
   netmask, the gateway of its network and its own address on the shared
   network to the group, encrypted and authenticated with a shared key;
   every member applies the newest configuration it receives, whatever
   its CARP state.  DCARP does not replace CARP: CARP still elects the
   Master, and DCARP only distributes what CARP needs to be configured
   with, and what the members need to route in either state.

   This version of DCARP handles IPv4 only.

1.2.  Terminology

   CARP interface:  The interface of a member that carries the virtual
      address managed by DCARP.

   Master, Backup, Init:  The CARP states of a member's CARP interface.
      A CARP interface without any address does not take part in the
      election and stays in Init.



Hallqvist                  Expires 26 May 2027                  [Page 3]

   Configuration:  The virtual address, its netmask, the gateway on its
      network and a Backup Gateway, together with a Generation.

   Backup Gateway:  The address of the Master on another network that
      the members share, through which the other members route while
      they are Backups.

   Generation:  The time at which the address of a Configuration was
      obtained, used to decide which Configuration is the newest
      (Section 6).

   Priority:  The CARP demote count, advertisement base and
      advertisement skew of a member, which CARP uses to elect the
      Master.  Lower values are better.

   Sync interface:  The interface on which a member sends and receives
      DCARP messages: the CARP interface unless configured otherwise
      (Section 5).

2.  Protocol Overview

   All members of a CARP group run DCARP and share a 256-bit key.  The
   Master sends a DCARP message to an IPv4 multicast group on the Sync
   interface when it becomes Master, when the address of its CARP
   interface changes, and periodically.  The message carries the
   Master's Configuration, its Priority, and fields that let receivers
   detect replays.  It is encrypted and authenticated with
   XChaCha20-Poly1305.

   A member that receives a valid message takes the Configuration if its
   Generation is newer than its own, in every CARP state, so a Backup
   that has become Master because it rejected the Master's
   advertisements still takes the new address.  Of the same Generation,
   a member that is not Master takes it from any sender, since CARP has
   elected the sender; a Master takes it only if the sender has a better
   Priority.  Taking a Configuration makes its address the only IPv4
   address of the CARP interface, which restarts CARP on that interface;
   with the same addresses as the Master, the member then accepts the
   Master's advertisements and returns to Backup.

   DCARP does not change routes.  It makes the Configuration available
   to the local system, which uses the gateway when the member becomes
   Master (Section 10).

   Backup Gateway (4 octets):  The sender's IPv4 address on another
      network that the members share, which the other members are to use
      as gateway while they are Backups, or 0.0.0.0 if there is none.

   Lease Time (4 octets):  The number of seconds the DHCP lease of the
      Address lasts from the Generation on, or 0 if the sender knows of
      no lease.  Receivers MAY use it, for example to tell when the
      lease runs out.  The field was reserved before, so that earlier
      senders set it to zero and earlier receivers ignore it.

   Sender (8 octets):  A random value the sender chooses when it starts,
      which identifies it for replay detection.

   Sequence (8 octets):  A counter of the sender, 1 in its first message
      and incremented by one in each message it sends.

   Timestamp (8 octets):  The time the message was sent, as a signed
      number of seconds since 1970-01-01T00:00:00Z.

   Generation (8 octets):  The Generation of the Configuration, a signed
      number of seconds since 1970-01-01T00:00:00Z, or 0 (Section 6).

   Demote (4 octets), Advbase (1 octet), Advskew (1 octet):  The
      sender's CARP demote count, advertisement base and advertisement
      skew: its Priority.

   Reserved (2 octets):  Senders MUST set it to zero; receivers MUST
      ignore it.

4.  Encryption and Authentication

   All members of a group share a 256-bit key.  How the key is generated
   and distributed is outside the scope of this document; it MUST have
   at least 256 bits of entropy [RFC4086].

   A sender encrypts and authenticates each plaintext with
   AEAD_XChaCha20_Poly1305 [I-D.irtf-cfrg-xchacha], which extends the
   AEAD construction of [RFC8439] to a 192-bit nonce.  The inputs are:

   Key:  The shared key.

   Nonce:  24 octets the sender MUST choose at random for each message.
      With 192 bits, random nonces do not repeat in practice, and no
      state is needed to keep them unique.

   Additional data:  The 8 octets of the ASCII string "DCARP 1" followed
      by a zero octet, which binds the key to this protocol and version.




Hallqvist                  Expires 26 May 2027                  [Page 7]

Internet-Draft                    DCARP                    November 2026


   Plaintext:  The 64 octets of Section 3.2.

   The message is the nonce, followed by the ciphertext and the 16-octet
   authentication tag.  A receiver MUST authenticate a message before it
   uses any of its contents, and MUST discard messages that fail.

5.  Transport

   Messages are sent as UDP datagrams to the IPv4 multicast group
   224.0.0.18, destination port 3522, with a time to live of 1
   (Section 13 discusses these values).  An implementation SHOULD allow
   both to be configured.

   By default the Sync interface is the CARP interface.  An
   implementation MAY allow another interface to be configured, for
   example a dedicated link between the members.  A member MUST join the
   group on its Sync interface, and MUST select the interface explicitly
   rather than by address: the address of the CARP interface changes,
   and may be missing.  It MUST discard messages received on any other
   interface, and messages whose payload is not exactly 104 octets.

   A Master whose CARP interface is the Sync interface cannot send while
   CARP restarts after an address change (Section 9); it sends once it
   is Master again.

6.  Generations

   Every Configuration has a Generation: the time its address was
   obtained or its DHCP lease last renewed.  Comparing Generations tells
   which of two Configurations is newer.  A member keeps the Generation
   of the Configuration it holds:

   *  When it starts, the Generation is that of the Configuration it
      held before for the address its CARP interface has, which it keeps
      in stable storage, or 0 if there is none.

   *  When the address of its CARP interface changes other than by
      DCARP, for example when the DHCP client obtains a new address, the
      Generation becomes the current time, or one more than the
      Generation it held if that is not earlier.

   *  When it takes a Configuration (Section 8), it adopts the
      Configuration's Generation.








Hallqvist                  Expires 26 May 2027                  [Page 8]

Internet-Draft                    DCARP                    November 2026


   *  As Master, before sending, it learns from its DHCP client when the
      client last obtained or renewed the lease of the address.  Each
      such time is a new Generation: that time, or one more than the
      Generation it held if that is not earlier.  A renewal does not
      change the address, but is a new Generation, so that the other
      members learn of it.

   While a member runs, its Generation never decreases.  A member MUST
   NOT take the time at which a lease was stored, for example the
   modification time of a lease file, for the time of its latest
   renewal: DHCP clients commonly store a lease when they obtain it, but
   not when they renew it, so that a Backup's stored lease can be newer
   than the Master's Generation.

   Generations use wall-clock time, so the members' clocks MUST be
   synchronized, for example with NTP; see also Section 12.

7.  Sending

   A member whose CARP interface is Master and has an IPv4 address sends
   a message with its Configuration:

   *  when it becomes Master;

   *  when the address of its CARP interface changes, as soon as the
      interface is Master again (Section 5); and

   *  every Interval seconds otherwise.

   The periodic messages let members that start later, or that missed a
   message, learn the Configuration.  The Interval MUST be shorter than
   the maximum age of Section 8.1; the RECOMMENDED value is 10 seconds.

   The Address and Netmask are those of the CARP interface; if it has
   several IPv4 addresses, the sender uses one of them consistently.
   The Gateway is the one the provider of the address gives: the gateway
   of the member's default route if that route goes through the CARP
   interface, as a DHCP client adds from the lease.  A member that has
   become Master may still route via the previous Master, through
   another interface; it then sends the Gateway of the Configuration it
   last took or sent, if that is on the network of the Address, and
   otherwise 0.0.0.0.  The Gateway is not configured by the operator.
   The Backup Gateway is the sender's own address on another network the
   members share, which the operator configures, or 0.0.0.0.  Demote,
   Advbase and Advskew are the sender's current CARP values; the demote
   count is the sum over the groups the CARP interface belongs to, as
   CARP computes it.

8.  Receiving

8.1.  Validation

   A member discards a message, and SHOULD log its source address and
   the reason at a limited rate, if:

   1.  it was received on another interface than the Sync interface, or
       is not 104 octets long (Section 5);

   2.  it does not authenticate (Section 4);

   3.  its Timestamp differs from the member's clock by more than the
       maximum age, 30 seconds; or

   4.  its Sequence is not higher than the highest Sequence accepted
       from the same Sender.  A member MUST remember the Sequence of the
       Senders it heard from most recently, at least as many as the
       group has members and at least eight; a restarted member is a new
       Sender.

   A member ignores its own messages, whose Sender is its own, and
   discards messages of an unknown Message Type.

8.2.  Acceptance

   A member takes the Configuration of a valid message if:

   *  its Generation is greater than the member's Generation, in any
      CARP state, Master, Backup or Init;

   *  its Generation equals the member's Generation and the member is
      Backup or Init.  Only a Master sends, and CARP has elected it,
      possibly with a worse Priority than the member's, as when a member
      returns without preemption.  A member in Init sends nothing, and
      one whose CARP interface has no address yet gets it this way
      (Section 9); or

   *  its Generation equals the member's Generation, the member is
      Master, and the sender's Priority is better than the member's own:
      a lower Demote, or an equal Demote and a lower Advbase, or equal
      values of both and a lower Advskew, which is the order in which
      CARP compares advertisements; or an equal Priority and a lower
      Sender, compared as unsigned 64-bit integers.

   It MUST discard, and SHOULD log, any other.  The Generation comes
   first because after a failover the member with the worse Priority may
   hold the newer lease; the Priority decides only between



Hallqvist                  Expires 26 May 2027                 [Page 10]

Internet-Draft                    DCARP                    November 2026


   Configurations of the same Generation, and there only for members
   that are Master at the same time and receive each other's messages
   but not each other's advertisements, for example over a separate Sync
   interface while the network of the CARP interface is split: exactly
   one of them takes the other's Configuration.

8.3.  Taking a Configuration

   To take a Configuration, a member adopts its Generation and makes its
   Address, with its Netmask, the only IPv4 address of the CARP
   interface: it adds the address if it is missing and then removes all
   other IPv4 addresses of the interface.  It MUST NOT keep an old
   address, since CARP authenticates over all addresses (Section 9), and
   it SHOULD add the new address before removing the old ones, since a
   CARP interface without an address leaves the election.

   A member that is Backup SHOULD put the address of the Configuration
   it holds back when its CARP interface has no IPv4 address: shortly
   after something else removed it, such as its DHCP client at the
   expiry of a lease that it obtained while the member was Master,
   unless another address has turned up meanwhile; and when the
   interface becomes Backup without it.  Without the address, CARP
   rejects the Master's advertisements: an interface that keeps another
   address, such as an IPv6 link-local one, makes the member Master
   beside the Master, and one without any leaves the election.  A Master
   MUST NOT do so, since its address follows its DHCP lease.

   Each change of the addresses restarts CARP on the interface, so a
   member MUST NOT change them when the address is already the only one,
   and SHOULD do nothing when the Configuration equals the one it took
   last.  Periodic messages thus cause no changes.

   A member MUST NOT change its routes because of a Configuration.  It
   makes the Configuration available locally, including the sender's
   Backup Gateway (Section 10).

9.  Interaction with CARP

   CARP computes the authentication of its advertisements over, among
   other things, the sorted set of IPv4 addresses of the CARP interface
   [CARP].  When the Master's address changes:

   1.  CARP on the Master restarts: the interface passes through Init
       and Backup and becomes Master again after about three
       advertisement intervals.  Meanwhile it neither sends
       advertisements nor, on the CARP interface, DCARP messages.





Hallqvist                  Expires 26 May 2027                 [Page 11]

Internet-Draft                    DCARP                    November 2026


   2.  The Backups reject the Master's advertisements, whose
       authentication now covers a different set of addresses.  A Backup
       whose master-down timer expires before it has the new address
       becomes Master as well.

   3.  When the Master is Master again, it sends its Configuration,
       whose Generation is newer.  Every other member takes it, in its
       current state, and changes its address, which restarts CARP on
       its interface.  With the same addresses as the Master it accepts
       the Master's advertisements and becomes Backup again.

   4.  A member that became Master in step 2 sends its own, older
       Configuration.  The Master, and any member that already holds the
       new Configuration, discards it as older.

   If the new Configuration reaches a Backup before its master-down
   timer expires, the Backup takes it as Backup and step 2 does not
   occur.  If the message is lost, the periodic messages repeat it.  The
   interruption of the Master's own service while CARP restarts is not
   avoided by DCARP.

   A member whose CARP interface has no address stays in Init.  Since a
   member takes Configurations in Init as well, such a member obtains
   its address from the Master and then joins the election.

10.  Local Use of the Configuration

   DCARP does not set routes, so that it does not compete with the tools
   that already follow CARP state changes on a member, such as a daemon
   that changes the default route when the CARP interface becomes Master
   or Backup.  A member SHOULD make the Configuration it holds, as
   Master or Backup, available to such tools, for example in a file.
   When the member becomes Master, they can then route via the Gateway
   at once, before any DHCP exchange of the new Master completes; when
   it becomes Backup, via the Backup Gateway.  Appendix A describes how
   the reference implementation does this.

   The Backup Gateway a member makes available is that of the member it
   last took a Configuration from, also while it is Master itself, and
   across restarts; its own is of no use to it.  When it falls back to
   Backup, the tools route at once, before a message from the new Master
   arrives, and the members' addresses on the shared network do not
   change.  A member that has never taken a Configuration has no Backup
   Gateway, and the tools need another default.

   With more than two members, the Master can change while a member
   stays Backup: its own CARP state does not change, but its Backup
   Gateway does.  Tools that act only on the member's CARP state changes



Hallqvist                  Expires 26 May 2027                 [Page 12]

Internet-Draft                    DCARP                    November 2026


   miss this.  A member SHOULD therefore notify the tools whenever the
   Configuration it holds changes, as well as when its CARP state
   changes.

11.  Operational Considerations

   *  All members MUST use the same key, group and port, and Sync
      interfaces on the same network.  Implementations SHOULD log a
      fingerprint of the key, such as the first octets of a hash of it,
      so that operators can compare the keys without revealing them.

   *  The members' clocks MUST agree within the maximum age of 30
      seconds, and closely enough that Generations compare correctly.

   *  The DHCP client of the shared address runs on the CARP interface
      and gets no lease on Backups, whose CARP interface does not pass
      traffic.  A DHCP client left running on a Backup removes the
      address when the lease it obtained as Master expires
      (Section 8.3).  On some systems the DHCP client also changes the
      local resolver configuration; operators may want to prevent that
      on the CARP interface.

   *  A member restarted without the Configuration it held has
      Generation 0.  Until its address changes or it learns of its DHCP
      lease, the other members discard the Configuration it sends as
      Master if they hold a newer one.

12.  Security Considerations

   The shared key protects the confidentiality, integrity and
   authenticity of the Configurations.  Every holder of the key is
   trusted: a holder can make the other members take any address and
   gateway by sending a Configuration with a later Generation, and the
   Backups by sending one with the same Generation.  The compromise of
   one member therefore compromises the group, and the key needs the
   same protection as the members' administrative credentials.

   The Timestamp and Sequence stop replays.  A member discards a message
   older than 30 seconds, and a message whose Sequence it has already
   seen from the same Sender.  Within 30 seconds, a recorded message can
   be replayed to a member that does not remember its Sender, for
   example after a restart; such a message carries a Configuration that
   was current 30 seconds earlier, and is discarded anyway if the member
   holds a newer Generation.







Hallqvist                  Expires 26 May 2027                 [Page 13]

   DCARP depends on synchronized clocks.  An attacker who can move a
   member's clock, for example by attacking its time synchronization,
   can make it discard valid messages, accept older ones, or give its
   own Configurations Generations that win over newer ones.

   The encryption hides the Configuration, the Sender, Sequence and
   Priority, but not the existence, size and timing of the messages or
   the source address of the sender, which is visible to anyone on the
   network of the Sync interface.  With the default Sync interface that
   is the network of the shared address, often a provider's network.  A
   separate Sync interface on a trusted network hides even that.

   Anyone on that network can send datagrams to the group.  Each costs
   the receiver one authentication attempt; implementations SHOULD limit
   the rate at which they log discarded messages.  The time to live of 1
   and the link-local multicast group keep the messages on the local
   network.

   Nonces are random and 192 bits long, so their reuse under one key is
   negligibly likely.

   Tools that set routes from a Configuration act on data that is
   authenticated, but chosen by another member.

13.  IANA Considerations

   This document makes no requests of IANA.  The reference
   implementation uses the multicast group 224.0.0.18, which is assigned
   to VRRP [RFC9568] and also used by CARP, and UDP port 3522, which is
   not registered for DCARP.  A version of this document intended for
   wider deployment would need a port assignment from the Service Name
   and Transport Protocol Port Number Registry [RFC6335], and either a
   multicast group assignment [RFC5771] or a justification for sharing
   the VRRP group.

Appendix A.  Reference Implementation

   dcarpd(8) implements DCARP on OpenBSD.  It derives the 256-bit key as
   the SHA-256 hash of a key file, sends every 10 seconds, and remembers
   64 Senders.  As Master it asks dhcpleased(8) over its control socket,
   read-only as "dhcpleasectl -l" does, when the lease of the address
   was last acknowledged and how long it lasts; after a malformed answer
   or none, it does not ask again until it is told to, lest a dhcpleased
   whose messages differ take the question for a request for a new
   lease.

   It writes the Configuration it holds to a state file of shell
   variable assignments, which it replaces atomically:

   DCARP_INTERFACE=carp0
   DCARP_ADDRESS=192.0.2.10
   DCARP_NETMASK=255.255.255.0
   DCARP_GATEWAY=192.0.2.1
   DCARP_BACKUP_GATEWAY=192.168.1.2
   DCARP_GENERATION=1793625676
   DCARP_LEASE_TIME=86400
   DCARP_LEASE_EXPIRES=1793712076

   It starts with the Generation of the state file, and as Backup puts
   the address back as Section 8.3 describes.

   ifstated(8) sources the file and routes via DCARP_GATEWAY when the
   CARP interface becomes Master, and via DCARP_BACKUP_GATEWAY when it
   becomes Backup, so that its configuration is the same on every
   member.  A complete ifstated configuration is distributed with the
   implementation.  The Backup Gateway is the -g option of dcarpd.

   With more than two members, dcarpd runs the program given with its -x
   option, with the state file and the CARP state as arguments, whenever
   it writes the state file and whenever the CARP state changes, one run
   at a time; the program sets the routes.

   The implementation comes with regression tests that run two or three
   members in separate routing domains of one host, including the split
   of Section 9, failovers among three members, a member returning
   without preemption, Masters of equal Priority, replays, tampered and
   stale messages, messages with another key, a Backup that loses its
   address, and renewals of the lease.
